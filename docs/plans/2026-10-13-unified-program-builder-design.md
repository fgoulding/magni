# Unified program builder and JSON import

## Approved direction

The user wants one understandable program-creation experience for manually authored and LLM-generated programs. After reviewing the proposed design, the user selected **private draft to review** for direct submissions and required the visible label **Import JSON**, not “Import from AI.” Proceed within the existing implementation/release authorization.

Programs offers three actions: **Choose a program**, **Build a program**, **Import JSON**. Ready rich templates, manual drafts and JSON imports converge on the same day-based visual builder and review/start flow. Original training systems remain accessible with their existing progression semantics; do not silently convert proportional AMRAP rules into a different evaluator.

## Human-first editor

Show program name, units, saved status and Review & start. A desktop day outline selects a full day's exercise and superset cards. On phones use a labelled day selector. A superset displays its pair together, with an honest round count when all exercises have matching sets. Ordinary rows expose exercise name, sets, rep range and optional working weight. Add exercise, Add superset, Add day, duplication and accessible reorder actions are direct controls.

Rest, effort, tempo, notes and progression expand in the exercise's own context. Summarize configured advanced fields even when collapsed. Equal sets can use a compact prescription; differing set roles, reps, loading or cues require visible individual-set summaries and an edit control. A compact edit must not flatten differences or discard hidden fields. Begin with one repeating week; show additional weeks/blocks when present or deliberately requested. Keep the existing advanced authoring capabilities accessible while sharing the same stored document and draft identity.

Keep normal form scrolling, semantic design tokens, labelled native controls and 44px targets. Review includes actual workout content, schedule and one Start program action. Creation and retries preserve stable draft identity. Imports create a fresh private draft rather than replacing an open program. Starting training is separate from submission. Existing active-change review and frozen started/completed workouts remain intact.

### Layout and editing priorities

- Programs is the only program-library landing page. Present the three entry actions together, with drafts and existing programs below. Do not repeat a separate workspace/defaults landing page or add another creation menu containing the same actions.
- The editor leads with the program's name rather than “Program workspace.” Use a roughly 240px outline beside one editing canvas on desktop, with 16px card padding and 12–16px field gaps. At phone widths, keep the selected day above its cards; reveal a labelled week selector only when the document has multiple weeks. Never hide an imported week, block or deload marker simply because a new blank program starts with one week.
- A day header contains its editable name and Duplicate day. Keep Add exercise and Add superset at the end of that day's list. Empty days show those same actions and a short instruction. Group membership is shown spatially in a single superset card, not entered as matching group-name text in separate exercise forms.
- Show exercise name, set count, rep target and working-weight context without opening details. A matching pair may read “Superset A · 5 rounds”; unequal counts read, for example, “Superset A · 5 / 3 sets.” Do not offer a single round-count value that quietly rewrites unequal sets. Distinguish bodyweight and percentage-of-max prescriptions from blank optional working weights.
- Compact fields edit only the values they name. Mixed prescriptions show concise per-set summaries with warm-up/work roles and load methods intact. Keep referenced AMRAP/designated sets identifiable when reordering or editing; do not renumber their identity by appearance. Configured progression and shared scope remain summarized beside the exercise, and editing them opens in the same context. Complex imported content must not require the old global tabs merely to inspect what it will do.
- Add, duplicate and reorder retain focus predictably and announce the result. Reordering always has named Move earlier/later controls. Duplicate copies the selected content, while any progression-sharing effect is stated rather than implied by exercise name. Removal has a labelled action and recoverable undo; routine additions do not need confirmations.
- Review shows actual day/superset content and schedule, with Change links returning to the relevant context. A repeating one-week program uses familiar duration wording; multiweek programs also show the resulting total weeks and workouts so repetition is unambiguous. Start program is the one scheduling action. Draft save status stays visible but quiet; a failed save retains edits and provides retry.

Keep the primary action in normal document flow with bottom-navigation clearance. At 320, 375 and 393px, stack fields before their labels or decimal values become cramped; preserve full exercise names. Enlarged text can increase page height. Essential content must not depend on hover, dragging or color alone.

## One public file contract

Expose one explicitly discriminated, versioned Magni program JSON contract based on the rich document's semantic capabilities. Separate reusable program content from optional personal setup defaults; a reusable file must not require an actual start date. Existing rich files and compact catalog files remain accepted through named adapters, never a lossy rich-to-compact conversion. New exports use the public contract and round-trip all authored rules, notes, roles, set overrides and identity relationships. Publish a machine-readable schema, example and copyable authoring instructions. Unsupported or malformed values produce field-specific errors instead of being discarded.

Exercise history identity, appearance identity, progression sharing and set IDs remain distinct. New imports scope/remap portable identity once; retries return the same saved draft. They cannot claim another user's history identity. In-place edits preserve existing IDs and designated-set references.

## Direct submission and import UI

Import JSON accepts a native file picker and pasted JSON. It shows useful validation messages, retains input on errors and opens the imported draft in the same builder. Download example JSON, schema documentation and Copy AI instructions are secondary utilities; the feature itself is always named Import JSON.

File and paste are two input methods within Import JSON, not separate destinations. Keep the selected filename or pasted text visible while validating. The submission action is **Import as draft**, followed by the common builder with a brief **Imported as a private draft** status. No training is scheduled at this point. An imported program is private regardless of whether it arrived through the browser or a direct request.

Distinguish errors by what the user can fix: unreadable/oversized file; malformed JSON; unsupported file version; or invalid program content. Use a concise summary with human locations such as “Day 2 → Superset B → Overhead press: enter a positive rep count,” and expand the relevant field when an editable draft exists. JSON paths and parser positions belong in optional technical details, useful for repairing generated files. Never invent a line number or silently remove an unsupported field. Preserve pasted text/file context on validation and network errors, announce status changes, and keep retry tied to the same import attempt. Invalid input must not replace or navigate away from an existing draft.

An optional Direct upload section provides a revocable per-user import-only credential. Direct requests create private drafts and return a review URL. Credentials cannot start programs, mutate active training, read unrelated data or publish global defaults. Store only credential hashes; show the secret once. Require authentication, bounded input, idempotency and ownership checks. Browser writes retain same-origin protection. A narrow proxy exception must delegate to actual route authentication, never bypass it.

Keep Direct upload collapsed below the ordinary upload form so account credentials do not become a required creation step. Its copy should state that submissions create private drafts to review. Name credential creation/revocation explicitly; do not expose a credential in general Copy AI instructions, program exports, error details or saved examples.

The existing owner CLI remains the authority for global catalog publication. Personal upload does not become a global default. Reuse owned drafts and transactional activation rather than creating another training engine. An additive schema migration is justified for credentials and import receipts; populated upgrade, backup/restore and rollback evidence are required.

## Research and alternatives

The designer recommended day-based cards over a mandatory wizard (cumbersome repeated edits) or spreadsheet-only editor (poor superset and phone presentation). Keep essential exercise/sets/reps visible and disclose specialist fields locally. Sources: [WAI Forms](https://www.w3.org/WAI/tutorials/forms/), [GOV.UK Details](https://design-system.service.gov.uk/components/details/), [File upload](https://design-system.service.gov.uk/components/file-upload/), [Check answers](https://design-system.service.gov.uk/patterns/check-answers/), [WCAG Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html).

WAI/GOV.UK guidance informs these product recommendations; it does not prescribe this exact layout. WCAG 2.2 AA requires a non-drag alternative for applicable dragging interactions. Magni's 44px target convention is a separate product requirement. Acceptance includes keyboard entry and reorder, errors that retain input and identify corrections, 320px reflow, 375/393px normal and enlarged text, desktop review, mixed imported sets, decimal weights, and final-action reachability. Screenshot evidence and remaining visual findings are recorded below; browser-emulated renders do not verify physical iPhone behavior.

Audit identified three current representations: rich editor documents, a smaller runtime catalog format and legacy original-system snapshots. Unify the authoring interface and public interchange first while preserving existing evaluators. A wholesale database/program conversion is outside this change.

Preserved coordinator-produced screenshots before the next test run in `.playwright/unified-program-builder/design-review/`, retaining the test-result subdirectories. Independently inspected the full-body `simple-program-320.png`, `simple-program-375.png` (20px dark), `simple-program-393.png` (light), `simple-program-1280.png`, `simple-program-weights-375.png` and `simple-program-review-375.png` WebKit renders; also inspected representative Chromium full-body renders, plus WebKit `manual-builder.png` and `imported-mixed-sets.png`. These cover iPhone 13 mini/16 viewport widths and a desktop-width layout, not hardware tests. The wide WebKit project keeps an iPhone user agent and displays its install banner.

Observed strengths: supersets keep both exercises together; essential labels and group counts are clear; manual copied-day sharing is stated explicitly; imported top/back-off sets retain distinct labels and loads; bodyweight is distinct from an optional working weight. The focused `42.5` weight at 375px/20px stays readable beside the native stepper. No visible horizontal clipping was found in the supplied 320/375/393px states. Desktop outline and aligned fields make the selected day easy to scan. The review's Start program action is visibly clear above the phone navigation.

Three actionable findings were recorded in this first render and resolved in the follow-up below:

1. **Repeated technique text makes default programs unnecessarily long.** Squat, one-arm row and Spoto descriptions repeat the same cue inside one visible paragraph. `simple-program-weights-375.png` shows the row cue twice around “Choose your working weight before logging.” Deduplicate the rendered summary without changing stored prescriptions; show concise rest/effort/tempo metadata and one technique cue, with full authored details available locally. Apply the same treatment in review, which currently repeats these paragraphs across all days.
2. **Mixed-set metadata loses its set context in the summary.** `imported-mixed-sets.png` shows a top set at 142.5 lb and two back-off sets at 115 lb, then one unlabelled line combining “120s rest · RPE 8 · Tempo 3–1–1 · 120s rest · RIR 2” and the entire progression policy. Associate differing effort/rest/tempo with the relevant named set. Show a short progression summary separately, with the full rule and failure behavior in its local disclosure. Retain every configured value; do not hide the fact that sets differ or flatten the imported rule.
3. **The long builder ends without its next action.** Review & start exists at the top, while the bottom of the day offers only Add, Export JSON and Advanced editing. Repeat the same Review & start action in the normal-flow footer before secondary file/advanced tools. This should open the same review, not introduce another step or fixed overlay.

The fixed bottom navigation appears partway down some full-page captures because it is fixed to the captured viewport; that alone is not evidence of a positioning defect. This review did not operate the browser, inspect credential behavior or rerun workflow assertions. Those checks remain owned by the coordinator/verifier.
